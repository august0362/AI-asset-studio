# Decisions

Short records. Format: **decision**, *why*. Add new entries at the end and never renumber them. Any contract-affecting entry also follows [CONTRACTS.md §12](CONTRACTS.md#12-contract-change-process).

## Architecture decisions

| ID | Decision | Why |
|---|---|---|
| D-001 | **Modular monolith with exactly three business modules: Interface, Models, Kaggle.** The frontend, backend and storage are separated inside Interface. | Small team, single local user. Clear boundaries without the operational cost of services. |
| D-002 | **The Kaggle module's Python package is `kaggle_connector/`**, not `kaggle/`. | A top-level `kaggle` package would shadow the official `kaggle` pip package and break the CLI/API. Approved by the owner on 2026-11-06. |
| D-003 | **CONTRACTS.md is canonical.** It is implemented as Pydantic v2 models in `models/contracts/` (with a JSON Schema export) and as hand-mirrored TS types. Shared JSON fixtures guard both sides. Version `1.0`: MINOR for additive changes, MAJOR plus `/api/v2` for breaking ones. | One source of truth that both agents can follow. Avoids codegen tooling in M1 before a backend exists. |
| D-004 | **Two-phase upload**: `POST /uploads`, then the job request references `upload_id`s. | Lets validation be re-run when the model changes without re-uploading files, and keeps uploads when the model changes (FR-G6). |
| D-005 | **Local filesystem + JSON metadata, atomic writes, no database.** | The MVP scale is a single user with a few hundred jobs. Files are easy to inspect. |
| D-006 | **One in-process worker thread per compute profile (concurrency 1). The frontend polls; no WebSockets.** | No broker needed. One active remote run per profile matches the single-session reality and simplifies status mapping. |
| D-007 | **Kaggle is accessed only through the official `kaggle` CLI, run as a subprocess** with the credentials placed in that process's env and an isolated `KAGGLE_CONFIG_DIR`. | Official tooling. Credentials never enter the global process env or files. Mocking is trivial. |
| D-008 | **Compute profiles and the Kaggle Terms of Use.** Kaggle's Terms of Use allow one account per person and prohibit operating multiple accounts. Rules: (1) a profile is one Kaggle account owned and operated by one person who has authorized its use (`authorization_confirmed: true` is required to enable it); (2) **M3 implements and enables exactly one profile**; (3) the user always selects the profile explicitly; (4) the system never selects, rotates or fails over between profiles, never pools or sums quota across profiles, and never resubmits a job on another profile; (5) automatic recommendation is limited to the accelerator **within** the selected profile. | Compliance and honesty. The owner has stated that three credentials exist and belong to three different people (A-02). Enabling more than one profile is deferred (DF-04). |
| D-009 | **Quota comes only from `kaggle quota --format json`** (CLI ≥ 2.2.1), cached for 5 minutes. Values are `null`/`unavailable` when it is missing or fails. Quota is never derived from assumed weekly limits. | Never fabricate (NFR-3). |
| D-010 | **Live CPU/RAM/GPU telemetry comes from a cooperating managed notebook**: a reporter thread (psutil + NVML, with an `nvidia-smi` fallback) prints `AAS_TELEMETRY` lines, which the connector reads with `kaggle kernels logs -f`. It is best-effort: it requires an executing notebook, may be delayed or missing, and batch logs are not a guaranteed real-time metrics service. GPU0 and GPU1 are reported independently. TPU metrics are `unsupported` in the MVP. | Standard status endpoints do not expose machine metrics. The log stream is the only official channel available. |
| D-011 | **Deterministic resource planner** (CONTRACTS §7): filter by accelerator kind, then check VRAM, session limit and quota with `safety_factor 1.5` and `overhead 600 s`. Errors block, warnings do not. | Explainable, testable, and not a scheduler. |
| D-012 | **Accelerator abstraction**: models declare `accelerator_kind`s (`cpu`/`gpu_cuda`/`tpu`) and VRAM. The Kaggle module's catalog maps `accelerator_id` → Kaggle `--accelerator` value, device count, VRAM and session limit. | Keeps Models independent of Kaggle and Kaggle independent of models. |
| D-013 | **Strict validation, no silent discard**: unknown fields and options are rejected. The backend is authoritative, and the frontend mirrors the same rules as pure functions. | FR-G4/FR-G5. One error code set across both sides. |
| D-014 | **Mock mode is first-class**: `MockApiClient` (frontend, M1) and `MockKaggleClient` (backend, M2), with the same contracts, state sequence, log and telemetry protocol, and configurable resource scenarios. | Every milestone up to M3 is testable without Kaggle or a GPU. |
| D-015 | **Retries**: at most 3 bounded in-job retries for transient remote reads and downloads. Submission is never retried automatically. A user retry creates a new job (`retry_of`). | Each run consumes quota, and failed jobs must stay auditable. |
| D-016 | **Mock GLB** comes from a small pure-Python glTF 2.0 binary writer (a colored box mesh with an embedded texture). The mock PNG is rendered with Pillow (prompt text + category color). | Real, previewable files without heavy 3D dependencies. |
| D-017 | **The Kaggle module adds `resources/` and `runtime/` sub-packages** next to `client/` and `jobs/`. | Quota, telemetry and planning, and the code that runs on Kaggle, have distinct responsibilities. They are still one module. |
| D-018 | **AI agents are development-time only**: Claude Code handles architecture, planning, integration and debugging, and Codex handles module implementation, tests, review and fixes. They share the docs and never edit the same files at the same time. Runtime agent features are deferred (DF-10) and would live inside Interface. | No fourth module. Avoids conflicting edits. |
| D-019 | **M1 and M2 were built in parallel** (owner instruction, 2026-11-06), instead of M2 waiting for M1. Codex owns `interface/frontend/` and `design/stitch/`; Claude Code owns `interface/backend/`, `models/`, `kaggle_connector/`, `pyproject.toml` and the root `tests/`. Shared docs change only on the owner's instruction. | Saves calendar time. Both sides build against CONTRACTS v1.0, and mismatches are reported to the owner instead of being fixed unilaterally. |
| D-020 | **Contract v1.0 clarifications** approved by the owner on 2026-11-06. They document what both sides already implement, so the version stays `1.0`: (1) `GenerationResult.compute.resource_plan` is the full §7.3 `ResourcePlan`; (2) `GET /jobs/{id}/artifacts` returns `{contract_version, artifacts}`; (3) `POST /validate` returns 400 for a non-JSON body and 200 otherwise; (4) `GET /uploads/{id}` returns the `UploadRecord`; (5) an unknown route is 404 `PATH_INVALID`, a wrong method is 405 `REQUEST_FIELD_INVALID`, and `PATH_INVALID` is otherwise 400; (6) `ComputeProfile.mode` may be `mock`; (7) `JobSummary.primary_artifact` is the full artifact; (8) a user-selected accelerator is the only candidate evaluated. | The examples were abbreviated or silent on these points. The frontend job page needs `estimate_basis`, and §1 requires `contract_version` on every top-level payload. |
| D-021 | **VRAM "not applicable" vs "unknown"**: a null `minimum_gpu_vram_bytes` is *unknown* only when the model lists it in `unknown_requirements`; otherwise it is *not applicable* and the planner skips the VRAM check (no `COMPUTE_VRAM_UNKNOWN`). The VRAM check applies to `gpu_cuda` accelerators only. | Removes a meaningless warning for CPU-capable models (e.g. `mock-t2d-basic` on a GPU) and matches the §2.1 rule on null requirements. The frontend planner already behaved this way. |
| D-022 | **Upload size is enforced while the body streams**: the backend stops reading at limit + 1 MiB of multipart overhead and returns `413 UPLOAD_TOO_LARGE`, whether or not `Content-Length` is sent. | Without it, the web framework would spool an oversized file completely before the size check. |
| D-023 | **Four color themes in two families** (owner request, 2026-11-06): coffee (`latte` light, `caffe` dark) and green (`mint` light, `matcha` dark), plus a light / dark / system mode setting. The theme is applied with semantic CSS tokens on `<html data-theme>`. [UI.md](UI.md) §1–§4 is canonical for colors and replaces the single dark "Obsidian" palette in `design/stitch/DESIGN.md`. The theme is a frontend-only preference stored in `localStorage`. Added to M1. | The owner wants light and dark modes with the given color moods. Pairing each light theme with a dark sibling keeps the app's character when the mode switches. Semantic tokens keep components theme-agnostic. |
| D-024 | **Vietnamese and English UI** (owner request, 2026-11-06), frontend only, with [UI.md](UI.md) §5–§9 as the canonical spec. A typed dictionary per language with no new dependency; English is the source and fallback. API payloads, error codes, logs and model names stay English, and errors are localized by `code` (already allowed by CONTRACTS §5.2), so the contract stays `1.0`. Added to M1. | The owner and users are Vietnamese. Keeping the backend English avoids a contract change and keeps logs searchable. |
| D-025 | **M3 uses profile `SUNNY` only** (owner, 2026-11-06). The owner asked for all three profiles (`SUNNY`, `ATUME`, `DUMA`) to be selectable. M3 still enables only `SUNNY`, as D-008 requires; the profile selector works for any number of enabled profiles, so `ATUME` and `DUMA` can be enabled later through DF-04 without new code. The owner approved spending a small amount of `SUNNY` GPU quota on the spike and smoke runs, and chose not to regenerate the tokens. | Kaggle's Terms allow one account per person and forbid operating multiple accounts. One person switching between accounts to get more GPU time would breach them and could get all three accounts banned. |
| D-026 | **Quota mapping (resolves DF-05).** `kaggle quota --format json` returns rows `{resource, used, remaining, total, refreshAt}` for `GPU` and `TPU`. Hours are strings with an `h` suffix (`"4.87h"`). They map to the six `*_quota_*_hours` fields, and `quota_reset_at` is the GPU `refreshAt`. `refreshAt` has no time zone and is **read as UTC** (assumption: `2026-11-07T00:00:00` is a Saturday, Kaggle's weekly reset). The CLI prints a version warning before every payload, so parsers skip non-payload lines. Unreadable values stay `null`. | Recorded 2026-11-06, CLI 2.2.4 (profile `sunny`). |
| D-027 | **Kaggle accelerators (resolves DF-06).** A real profile offers only the verified entries: `cpu` (no `--accelerator`) and `gpu_t4x2` (`--accelerator NvidiaTeslaT4`: 2 × Tesla T4 with 16106127360 B each, read via NVML; 4 vCPU; 31.3 GiB RAM). `gpu_p100` (no documented value) and `tpu_vm` (unverified) are left out of Kaggle profiles. The mock keeps the provisional catalog. The Kaggle value lives only in `kaggle_connector/resources/catalog.py`. Session limits stay at the provisional 12 h (A-04). | Verified with an 8-minute T4×2 run and CPU runs on 2026-11-06. Offering an unverified accelerator would make the planner promise something Kaggle may refuse. |
| D-028 | **Live telemetry through `kaggle kernels logs -f` works (resolves DF-07).** On a 4-minute run, the median sample latency was **1.1 s** (max 3.4 s) and all 24 samples arrived. The stream ends by itself when the run ends. The one-shot `kaggle kernels logs` returns nothing until the run has ended (it reads the saved log), so it is used only to fill gaps after the run. On T4×2, GPU0 and GPU1 arrived as separate NVML readings. | Far inside the 60 s target, so the app shows live CPU/RAM/GPU values during runs and needs no fallback. |
| D-029 | **Inputs: one private dataset per job (resolves DF-08).** `upload_inputs` creates `<owner>/aas-in-<job id>` (private, CC0 metadata) with a marker file the notebook uses to find the mount, waits until `datasets status` reports `ready`, and lists it in the kernel's `dataset_sources`. The dataset is **deleted** when the job ends, or straight away if the push fails. Kernel cleanup: see D-031 (2). | Jobs share no state, so there are no version conflicts. The user's images do not stay on Kaggle. One small image was ready in about 20 s. |
| D-030 | **KaggleCliClient design (M3).** (1) **Kernels:** one private kernel per job, with slug `aas-<job id>`, `enable_internet: false` and an explicit `--timeout` (the planned run timeout). (2) **Packaging:** a script kernel uploads only its code file, so `runner.py`, the adapter entrypoint and `job.json` are embedded in one generated `aas_kernel.py`. An entrypoint failure raises an exception, so Kaggle reports `ERROR`. (3) **Remote reference:** `remote_ref` is `<profile_id>/<kernel slug>`, so job files never store the Kaggle account name. CONTRACTS §3.4 shows `owner/aas-runner` only as an example. (4) **Profiles:** `AAS_ACTIVE_PROFILE` names the one enabled profile. The others in `AAS_COMPUTE_PROFILES` are listed as disabled, and their credentials are never read. (5) **Auth check:** `kaggle config view` returns the account the token belongs to. If that differs from the configured username, the profile is marked `invalid_credentials`; this catches swapped tokens. (6) **Post-push access errors:** `Cannot access kernel … (Permission 'kernels.get' was denied)` within 180 s of a push is treated as `queued`, because Kaggle may not have registered the new kernel yet. (7) **Status mapping:** `QUEUED` and `NEW_SCRIPT` → queued; `RUNNING` → running; `COMPLETE` → complete; `ERROR`, `CANCEL_REQUESTED` and `CANCEL_ACKNOWLEDGED` → error. Observed strings: `KernelWorkerStatus.RUNNING`, `.COMPLETE`, `.ERROR`. (8) **Refresh:** auth and quota refresh in the background every 5 minutes, so validation never calls the CLI. | Applies D-007, D-008, D-009, D-015 and CONTRACTS §10 to what the spike measured. |
| D-031 | **Owner decisions after the M3 spike (2026-11-06).** (1) **P100 and TPU are dropped** from Kaggle profiles for good: P100 is not offered by Kaggle, and TPU queues are too long to be useful. Only `cpu` and `gpu_t4x2` remain. The mock catalog and the CONTRACTS §6.1 example still list them until a coordinated contract/fixture change (CONTRACTS §12, with Codex). (2) **Kernel cleanup:** a job's kernel is deleted once the job completes, because its outputs and logs are already stored locally. A failed job's kernel is kept so the owner can inspect it on Kaggle and delete it by hand. This supersedes "kernels are kept" in D-029. (3) **Test switch** `AAS_KAGGLE_TEST_FAILURE=kernel_error`: every Kaggle run then fails on purpose inside the real notebook, and its log says so, so the UI's notebook-error path can be checked. Other failure types are checked in mock mode with `AAS_MOCK_FAILURE`. Off by default. | Owner request. Old kernels add clutter but no value once results are local. The switch costs no GPU when used with a CPU job. |
| D-032 | **Model weights are downloaded from the internet inside the Kaggle run (owner, 2026-11-06; resolves DF-12).** (1) A job whose model needs downloads runs with `enable_internet: true`. Mock models keep it off. (2) Only weights that download **without a login or token** are allowed (no gated Hugging Face repos), because a token would have to be put into the notebook, which CONTRACTS §10 forbids. (3) Each model record pins an exact repository revision, so a run always gets the same weights. (4) Python packages a model needs are installed with pinned versions in the same run. (5) **The owner chooses every real model** (M4, M5 and M6); Claude Code researches the candidates and reports, and does not pick. | Storing multi-GB weights locally and uploading them per job is not practical. Ungated, pinned downloads keep runs reproducible and keep secrets out of notebooks. |
| D-033 | **M4 model selection started with a benchmark outside the app (owner, 2026-11-06).** Five candidates (Animagine XL 4.0, SDXL Base 1.0, FLUX.2 [klein] 4B, Z-Image-Turbo, MOSS-Image-SFT) rendered the nine cases of the [Prompt Book](sources/M4_Text_to_2D_Prompt_Book_v1.md) in one Kaggle 2×T4 session, each as its own process on one GPU in fp16 (never bf16 on the T4), with pinned revisions and libraries; large text encoders ran first and were freed before the image model loaded; code paths were checked on free CPU sessions first. The one-off tool touched no contract, registry or `data/` and was deleted after the run; the results (images, settings, technical report) are in `M4_Text2D_Gallery.html` in the repository root (not committed, 73 MB). Claude Code did not rank the images; the owner chose (D-034). | Seeing all candidates on the same prompts is the cheapest way to choose, and the owner chooses every model (D-032). |
| D-034 | **Text→2D models chosen by the owner after the benchmark (2026-11-06; resolves DF-01 for `character`).** (1) **Kept:** Animagine XL 4.0, FLUX.2 [klein] 4B and MOSS-Image-SFT, all three offered side by side. **Dropped:** SDXL Base 1.0 and Z-Image-Turbo. (2) Each model's `runtime.estimated_runtime_seconds` is its **measured mean time for one image** on a Kaggle T4 in the benchmark (fp16, model-card settings, ~1 MP): Animagine **25 s**, klein **9 s**, MOSS **354 s**. This value excludes package installs, weight download and loading; the resource planner's `overhead_seconds` covers those. (3) The model picker shows that mean next to the name in parentheses (UI.md §9), so the owner can trade speed for look per job. (4) **Starting configuration (measured in the benchmark; libraries `diffusers==0.42.1`, `transformers==5.22.1`, `accelerate==1.15.0`, fp16 on one T4):** *Animagine XL 4.0*: `cagliostrolab/animagine-xl-4.0` @ `2b7c1b397761bf5bd3cc42e5b39ec99314a75a96`, SDXL pipeline, Euler Ancestral, 28 steps, CFG 5, tag-format prompt with the model card's quality and negative tags; prompts longer than 77 CLIP tokens are encoded in 75-token chunks that are concatenated. *FLUX.2 [klein] 4B*: `black-forest-labs/FLUX.2-klein-4B` @ `e7b7dc27f91deacad38e78976d1f2b499d76a294`, 4 steps, guidance 1.0, no negative prompt; the Qwen3 text encoder runs first and is freed before the transformer loads. *MOSS-Image-SFT*: `OpenMOSS-Team/MOSS-Image-SFT` @ `f972bd4b4b9e3852133cc5da954d87bc32cd8fb9`, the repository's `pipeline_moss_image.py`, 50 steps, CFG 3, shift 5, `uncond_skip_layers=[22]`, empty negative, VAE fp32; the 9B text encoder runs first, split 13 GiB GPU + host RAM. Plain fp16 stays finite only up to about 1 MP. Each model still goes through the M4 per-model tasks. | Owner review of the gallery. Showing the measured time keeps the speed difference visible: MOSS is about 40× slower than klein. |
